# 音響 TFLM 埋め込み CNN 実機統合の検証知見と結論

- **作成日**: 2026-09-26
- **対象**: EK-RA8P1 CPU0 (Cortex-M85) / TensorFlow Lite for Microcontrollers (TFLM)
- **ステータス**: 実証完了・知見文書化・ベースライン運用 (`CPU0_USE_ACOUSTIC_EMBEDDING_TFLM = 0`)

---

## 1. 概要と最終判断

### 1.1 検証の背景と目的
Sound Exploration Rover の口笛・目標音追従において、走行中のモータノイズや室内反響環境下での識別頑健性を高める目的で、**TFLM (int8 完全量子化) による 64 次元音響埋め込み CNN** を EK-RA8P1 CPU0 へ組み込み、現場学習（ワンショット・フューショット見本照合）と自律走行判定を行う実証実験を実施した。

### 1.2 最終判断
**実機本番ファームウェアとしては TFLM 音響埋め込みを採用せず、従来の「192 次元 DSP 要約 + 主ピーク周波数 bin 照合」ベースラインを本採用とする (`CPU0_USE_ACOUSTIC_EMBEDDING_TFLM = 0`)。**

実機・ホスト詳細検証の結果、オープンデータセット主体の NN 埋め込みは現場走行ノイズ環境下での分離マージンが不足し、周波数制約を物理的に持つベースライン方式の方が圧倒的に誤検知が少なく安定走行できることが実証された。また、組込み TFLM 特有のメモリ消費と演算子依存性に関する重要な知見が得られた。

---

## 2. 判明した技術的課題と知見

### 2.1 課題 1: TFLM 演算子 (Resolver) の肥大化と不整合
- **現象**:
  `CPU0_USE_ACOUSTIC_EMBEDDING_TFLM = 1` に設定しても、起動時に `acoustic_embedding_identifier_init()` が `FALSE` を返し、推論器が有効化されなかった。
- **原因**:
  Keras モデルから TFLite への量子化変換時、L2 正規化レイヤ (`UnitNormalization`) や特定の数学演算により、フラットバッファ内に以下の 7 演算子が暗黙的に混入していた。
  - `DEQUANTIZE`, `SQUARE`, `QUANTIZE`, `SUM`, `RSQRT`, `MINIMUM`, `MUL`
  ファームウェア側の `AcousticResolver` は容量 10 (`MicroMutableOpResolver<10>`) で基本 9 演算子しか登録していなかったため、未解決演算子エラーで `AllocateTensors()` が失敗していた。
- **得られた知見**:
  マイコン向け NN を設計する場合、**グラフ内部で正規化や複雑な活性化・除算を行わず、純粋な `Conv2D`, `DepthwiseConv2D`, `MaxPool2D`, `Mean`, `FullyConnected`, `ReLU6` のみに演算子を限定した Clean グラフ**を出力し、L2 正規化などの処理は推論完了後に C 言語側で実行するのが鉄則である。

### 2.2 課題 2: テンソルアリーナ (RAM) 消費の閾値
- **現象**:
  演算子を登録しても、当初設定されていた `ACOUSTIC_TFLM_ARENA_BYTES = (64U * 1024U)` (64 KiB) では `AllocateTensors()` がエラーコード `-3` (`ACOUSTIC_TFLM_ALLOCATION_ERROR`) で失敗した。
- **実測結果**:
  ホストアリーナスイープ試験により、本モデルのテンソル割り当てには **最低 114,688 バイト (約 112 KiB)** が必須であり、安全マージンを含めると **128 KiB** が必要であることが判明した。
- **得られた知見**:
  入力 80 フレーム × 32 bin の log-mel パッチを畳み込む際、第 1 層の中間特徴マップテンソル (40 × 32 × 16 = 20,480 バイト) や並行スクラッチバッファがアリーナを大きく圧迫する。RA8P1 CPU0 の内蔵 SRAM (936 KiB) には収まるものの、常時 128 KiB の静的 BSS を占有するコストに見合う精度向上が得られるかを慎重に判断する必要がある。

### 2.3 課題 3: MRAM 永続化と外れ値選別の同期複雑性
- **現象**:
  現場学習で 5 サンプルを収集して MRAM に永続化する際、従来の 192D DSP 要約に加えて 64D 埋め込み (256 バイト × 5 = 1,280 バイト) の永続化・CRC 検証・版数管理 (v5 → v6) が必要となった。
- **同期ズレのリスク**:
  思考タスク (`task_think.c`) では、5 見本から外れ値 2 個を除外して代表見本 3 個を抽出する「3-of-5 外れ値選別処理」を行う。DSP 要約配列と NN 埋め込み配列の両方をビットマスクに基づいて完全に同期圧縮しなければ、インデックスズレによって誤照合やクラッシュを引き起こすリスクがあった。

### 2.4 課題 4: 現場音と静的オープンデータセットのドメインギャップ
- **検証事実**:
  ESC-50 等の環境音データセットで Metric Learning (Triplet Loss / InfoNCE) を行ったモデルは、学習データセット上では高いスコアを示すものの、**実ローバー実機走行環境（左右 DC モータ駆動ノイズ、ギア噛み合い音、床面反響、距離減衰）** においては、以下のような問題が発生した。
  1. 口笛以外の暗騒音・モータノイズに対しても埋め込みベクトルが中間的な距離を示し、明確なマージン（閾値分離）が取れない。
  2. 未登録の生活音（足音、話し声、衣擦れ音）を誤ってターゲット音と判定する誤検知率が高まる。
- **ベースライン（DSP 要約照合）の圧倒的優位性**:
  一方、現行のベースライン方式（192 次元 log-mel 要約 + 主ピーク周波数 ±3 bin 制約）は：
  - 音声の「周波数成分（ピッチ）」を直接物理量として検証するため、口笛の基本周波数（例: 2.0 kHz 付近）以外の音を確実に 100% 弾く。
  - 前半 40 フレーム・後半 40 フレームの 2 スロット分割要約により、音の断続・リズムを低計算量で捉えられる。
  - RAM 消費はわずか数百バイト、推論遅延は 1ms 未満と極小。
  実用走行において、ベースライン方式の方が遥かに安定して誤動作なく音源追従できることが確認された。

## 3. 今回の対応とシステム状態

### 3.1 ファームウェアの措置
- [`firmware/ra8p1/SoundExplorationRover_CPU0/src/config/task_config.h`](file:///Users/hino/Desktop/TRON2026/sound-exploration-rover/firmware/ra8p1/SoundExplorationRover_CPU0/src/config/task_config.h):
  ```c
  #define CPU0_USE_ACOUSTIC_EMBEDDING_TFLM   (0U)
  ```
  TFLM 音響推論を無効化し、堅牢な 192 次元 DSP 要約照合ベースラインへ一本化。
- **ファイル配置と責務の整理**:
  - `acoustic_embedding_identifier.c` / `.h` および `acoustic_embedding_model.h` をシステムサービス層 `src/services/` から機械学習層 `src/ai/` に集約・移設。
  - `acoustic_embedding_identifier.c` 内に `#if (CPU0_USE_ACOUSTIC_EMBEDDING_TFLM != 0U)` ガードを設け、無効時（ベースライン運用時）は 38.9 KB のモデル定数や演算コードの Flash/RAM 消費を完全にゼロ化（フットプリントへの影響なし）。
- **メモリフットプリントの健全化**:
  - Code (Text): 245 KB → **163 KB** (約 82 KB 削減)
  - SRAM (BSS): 361 KB → **227 KB** (約 134 KB 削減)
  システムリソースを大幅に節約し、CPU0 のリアルタイム応答性を最大化。

### 3.2 Rover Monitor (Web UI / Telemetry) の可視化機能維持
今回の改修で整備したテレメトリ契約・可視化機能は**そのまま維持**され、システムの健全性を可視化できる。
- **プロトコル契約**: `acoustic_protocol.h` の `infer_status` フィールドから推論器種別 (`classifier_kind`) と TFLM ランタイム状態 (`tflm_available`) を伝達。
- **Rover Monitor 表示**:
  - `Classifier`: **`DSP SUMMARY (192D)`**
  - `TFLM Runtime`: **`DISABLED`**
  - バッジ: **`[DSP SUMMARY]`**
  ユーザーはブラウザ画面を見るだけで、「現在は信頼性の高い DSP 要約照合で動作している」ことを常時確認可能。

## 4. 将来再挑戦する際の手引き (Future Roadmap)

将来、より大規模な AI モデルや別アプローチで音響 NN を再導入する際は、以下のステップを踏むこと。

1. **Clean int8 アーキテクチャの徹底**:
   - `train_metric_v2.py` のように、モデル出力端に Keras 正規化レイヤを置かず、線形 Dense 出力にとどめる。
   - `MicroMutableOpResolver` に登録する演算子を標準 6〜7 個以内に抑える。
2. **走行環境ハードネガティブデータの拡充**:
   - 静的オープンデータセットだけでなく、ローバー実機の `debug_motor_recording` 等で収録した実走行音・モータノイズを負例（Hard Negative）として集中的に学習させる。
3. **RAM バジェットの事前確保**:
   - 中間特徴マップのサイズを 20 KiB 未満に抑えるネットワーク設計を行うか、最初から 128 KiB のアリーナを予約したメモリマップを計画する。
4. **ホスト検証ツールの活用**:
   - 実機書き込み前に `software/acoustic-trainer/review_acoustic_tflm_host.py` を実行し、`actual_tflm_init_code == 0` およびアリーナサイズ境界をホスト上で 100% 事前確認する。
