### 第1段の変更

`task_actuator` は1 ms周期ハンドラからイベントフラグで起床する。
ハンドラは `tk_set_flg()` のみを呼び、PWM、IPC取出し、エンコーダ保守はタスク文脈で行う。
時刻は `tk_get_otm()` のhi/loを64 bitへ合成し、前回との差を
`actuator_service_update(elapsed_ms)` → `encoder_housekeeping(elapsed_ms)` /
`drive_service_update(elapsed_ms)` へ渡す。
通知が重なっても1 ms分を反復して追い付かせず、実経過時間を1回適用する。

- RPMは100 ms以上経過した実際の窓で除算する。初回はカウント基準の取得のみ。
  カウント符号の折返しも定義済み演算で扱う。1窓の変位は2^31 count未満を前提とする。
- ランプは2 permille/ms。長い経過時間でも積がオーバーフローせず目標で止まる。
  PWMは5 ms基準で更新し、端数時間を次回へ持ち越す。遅延後は最新出力を1回反映する。
- 速度帰還の開始待ちは実時間150 ms。既定の速度帰還無効設定は継続。
- 無受信時間は飽和加算し、1500 msでsafe stop。期限切れをPWM更新前に判定する。
  新着指令は従来どおり期限を更新する。新しい目標へ過去の時間分のランプは適用しない。
- 緊急停止ラッチの解除には、引き続きアクチュエータ無効指令が必要。
- 待機／時刻取得異常では安全停止して周期通知を止める。
  生成・開始失敗時も作成済み周期資源を解放する。

μT-Kernelの `tk_sta_cyc()` は**初回だけ+1 tick**を加えるため、
通知開始直後は約2 msになる場合がある。以後は前の周期期限を基準に1 msで進む。
1 ms精度のOS時刻で、サブmsのジッタを測定したとは扱わない。

### 第2段の変更（2026-09-12）

- `task_status`も周期ハンドラ＋イベントフラグに移行。10 msの絶対周期で起床し、
  `tk_get_otm()`の実ΔtでLED反転と100 msの状態採取を管理する。初回だけ約11 msになり得る。
- 従来は送信中に100 ms待ちの計数が止まっていたため、7語送信時の採取間隔は通常約176 ms
  （16回×約11 ms、ソースからの見積り）だった。新方式は送信中も時間を数え、
  通常の採取開始間隔を100 msにする。
- 現行IPC契約の7語を維持し、1起床につき最大1語。通常は採取から最終語送信まで約60 ms。
  送信失敗時は同じスナップショットの同じ語を再送し、最終語成功時だけsequenceを進める。
  混雑中に来た採取期限は完了後に最新状態1件へまとめ、古い状態をまとめて送信しない。
- LEDは経過した反転回数の偶奇と端数を保持し、遅延分を連続点滅で消化しない。
- 作成・起動失敗では周期・タスク・フラグを解放する。実行中の時刻／待機異常では診断を記録し、
  状態通知と状態タスクを停止する。出力操作の所有権は駆動タスクに維持する。
  状態タスクの独立生存監視は今回追加していない。
- 周期ハンドラは駆動用と状態用の計2個（上限4個）。優先度12・スタック512 Bを維持。
  Arm生成コードで状態タスク本体のフレームは128 B。呼出先とカーネル文脈は別途必要であり、
  この値を実機スタック最大使用量とは扱わない。

CPU1 Generate + Clean Build成功、ホスト回帰8件成功（ASan/UBSan、警告のエラー化を含む）。
生成差分を整理した最終ソースのClean Buildも成功。変更ユーザーソースの警告0件、BSP警告87件。
最終ELFのtext/data/bssは24,220 / 8 / 13,076 B。実機への書き込みは行っていない。

#### 最初に行う診断変数の確認（モーター・サーボ電源OFF）

今回の周期カウンタの確認には、モーターやサーボを動かす必要はない。
以下の状態で、先に表示値と実行ファームウェアの一致を確認する。

| 接続・電源 | この確認での状態 |
|---|---|
| PC ↔ EK-RA8P1のJ10（デバッグUSB） | 接続したまま |
| EK-RA8P1の基板電源 | ON。現在の基板給電方法を維持する |
| BTS7960のB+ / B-へ供給するモーター用外部電源 | OFF |
| サーボ用外部電源 | OFF |
| J7 ↔ XIAO ESP32S3 | 周期カウンタだけなら接続不要。接続済みでもよい |

基板とモーターを同じ主電源から給電している場合、主電源を切るだけでは基板も停止する。
配線変更は電源を切って行い、駆動系への給電を分離してから基板だけを給電する。
J10接続だけで基板の給電条件を満たすかは、実際の基板電源設定による。
サーボ電源を基板の5 V端子へ付け替えない。

1. モーター・サーボ用外部電源をOFFにし、e² studioのCPU0/CPU1デバッグセッションを両方終了する。
2. CPU0/CPU1 projectをRefreshし、CPU0、CPU1の順でGenerate Project Contentを行う。
   両方をClean/Buildし、エラーがないことを確認する。
3. Debug Configurationsで **`SoundExplorationRover Debug_Multicore Launch Group`** を選んで開始する。
   この構成のCPU0側が両方のELFを書き込み、CPU1側がAttachする。
   **`SoundExplorationRover_CPU1 Debug_Attach`だけを実行しても、CPU1のフラッシュは更新されない。**
   読み込むファイルは、各projectの`Debug/SoundExplorationRover_CPU0.elf`と

### 変更

取得タスクが止まると、公開済みsnapshotの`age_ms=0`とvalidフラグも凍結する。
そこで`task_think`が`update_count`の進行を独立に観測し、`tk_get_otm()`の実時間で
最後の進行観測から200 ms以上なら走行不許可とする。回数を時間として加算しない。
初回のsnapshotだけでは進行を証明できないため、次の更新を観測するまで走行不許可。
カウンタの32 bit折返しは不一致として扱い、時刻逆行・取得失敗では不許可に戻す。

両走行モードへ適用する。音源追従は`motion_allowed=FALSE`、センサー走行はNULL入力で
既存の通常停止へ移行する。緊急停止ラッチを追加せず、更新が復帰すれば通常の状態遷移で再開できる。
元のvalid/距離/age判定は追加条件として維持し、共有snapshotやIPCの契約は変更しない。

`task_sensor_snapshot_get()`はmutexを待たず取得する。取得側がmutexを保持したまま止まっても、
思考側の監視まで永久待機させない。競合・取得エラーの場合も停止側に倒す。
テレメトリ側も取得エラーを扱う既存経路を使う。

`g_task_sensor_test_pause`（既定0）をLive Watchで1にすると、センサー取得ループだけを待機させる。
最後の正常snapshotを保持したまま、思考・指令タスクは動作を続けるため、今回の不具合を再現できる。
再起動時は0へ初期化し、0へ戻すと取得を再開する。通常運用では0にする。

CPU0の一時設定`CPU0_SOUND_MOVE_STEP_MS=10000`は通常値1000へ戻した。
