# 第4章: なぜint8なのか？（浮動小数点から整数への量子化の魔術）

前章までで、音の波形が「32個の浮動小数点数（float32）」というLog-Melスペクトログラムに変換されるところまで分かりました。
しかし、SEROVのファームウェアでは、この値をそのままAIに渡しません。
**「たった1バイトの符号付き整数（int8: $-128 \sim +127$）」** へと変換しています。

なぜ、わざわざ精度を落としてまで整数に変換（量子化）するのでしょうか？
本章では、量子化の圧倒的なメリットと、その驚くほどシンプルな計算の仕組み、そして組み込みAI開発者を悩ませる「丸めの罠」について解説します。

---

## 4.1 量子化（Quantization）とは何か？

### 日常の例え話: 「身長何センチ？」
友達に「身長何センチ？」と聞かれたとき、あなたはどう答えますか？
「172.38491... センチです」とは言いませんよね。「172センチ」と答えるはずです。
ミリ単位以下の細かい小数を丸めて捨ててしまっても、「友達が大柄か小柄か」を判断する上では何の影響もありません。

ニューラルネットワークも全く同じです。
ディープラーニングのモデルは、ノイズに強い柔軟な構造をしているため、**重みや入力データの数値を「小数点以下何桁もある細かな小数（float32）」から「粗い整数（int8）」に丸めても、認識精度はほとんど落ちません（通常 1% 未満の差）**。
この「小数を整数に丸める処理」を **量子化（Quantization）** と呼びます。

---

## 4.2 なぜint8にするのか？ 3大メリット

| 項目 | 32-bit 浮動小数点 (`float32`) | 8-bit 整数 (`int8`) | 効果 |
|---|:---:|:---:|:---:|
| **1つの数値のデータ量** | **4 バイト** | **1 バイト** | **メモリ 75% 削減（1/4）！** |
| **80フレームのイベントサイズ** | $80 \times 32 \times 4 = \mathbf{10,240\text{ B}}$ | $80 \times 32 \times 1 = \mathbf{2,560\text{ B}}$ | **USB転送が 4倍 高速化！** |
| **演算速度 (Helium MVE)** | 1クロックで 2〜4 演算 | 1クロックで **最大16演算** | **推論速度が 数倍〜十数倍 爆速化！** |

### ① メモリが 1/4 に圧縮される
第1章で学んだ通り、マイコンのSRAMは数万分の一しかありません。
入力データだけでなく、学習済みモデルのパラメータ（重み）もすべて `int8` に量子化することで、**モデルサイズとRAM消費量を一気に $\frac{1}{4}$ に圧縮** できます。

### ② USB転送パケットが 1/4 になる
ESP32-S3からRA8P1（CPU0）へUSB経由で特徴量を送信する際、10 KBあったデータが **たったの 2.5 KB** で済みます。通信パケット数が激減し、通信エラーのリスクも低減します。

### ③ Arm Cortex-M85「Helium MVE」による爆速並列演算（SIMD）
これが最も強烈なメリットです。
SEROVのメインCPUである **Cortex-M85** には、Arm最新のベクトル拡張機能 **「Helium（M-Profile Vector Extension: MVE）」** が搭載されています。
- 通常のCPU: 1回の命令で、1個の掛け算を行う。
- Helium MVE: 128ビットのベクトルレジスタを使い、**「8ビット整数16個」を1クロックで同時に一括計算（並列処理）** できる！

`float32` のままだと同時に4個しか計算できませんが、`int8` にした瞬間に **4倍の並列度（16並列）** で行列演算が疾走します。これにより、バッテリーをほとんど消費せずに、瞬時にAI推論を完了できるのです。

## 4.3 量子化の数式を世界一やさしく理解する

「量子化って難しい高等数学を使うのでは？」と思うかもしれませんが、驚くほど簡単です。
一般的なアフィン量子化の基本式は次の通りです：

$$q = \text{clip}\left(\text{round}\left(\frac{x}{\text{scale}}\right) + \text{zero\_point}, -128, 127\right)$$

- $x$: 量子化したい元の実数値（float）
- $\text{scale}$: スケール係数（刻み幅）
- $\text{zero\_point}$: ゼロ点（下駄履かせのオフセット）
- $\text{round}()$: 四捨五入
- $\text{clip}(v, -128, 127)$: $-128 \sim +127$ の範囲からはみ出た値を端っこで止める（飽和演算）

### SEROVの固定契約: なぜ「scale = 0.125, zero_point = 0」なのか？
SEROVの設計書（`docs/firmware/edgeai/README.md`）では、次のように固定されています：
- **`scale = 0.125`**
- **`zero_point = 0`**

これを上の式に当てはめてみましょう。
$\frac{x}{0.125}$ という割り算は、逆数を掛けると **$x \times 8$** になりますね！
$\text{zero\_point} = 0$ なので、足し算も不要です。

つまり、SEROVの量子化は、実質的に **「実数に8を掛けて四捨五入するだけ」** なのです！

```text
元のLog-Mel値 (float)      計算 ( × 8 )       四捨五入       int8量子化値
────────────────────────────────────────────────────────────────────────
      +0.50          ──▶    +4.00     ──▶      +4      ──▶      +4
      +1.25          ──▶   +10.00     ──▶     +10      ──▶     +10
      -0.31          ──▶    -2.48     ──▶      -2      ──▶      -2
     +20.00 (巨大音) ──▶  +160.00     ──▶    +160      ──▶    +127 (上限クリップ)
```
これなら小学生の算数でも計算できますし、マイコンも一瞬で計算できますね！

## 4.4 組み込み開発者を悩ませる「丸めの罠」

一見簡単に見える量子化ですが、**「Pythonとマイコン（C言語）で出力が1ビットだけ食い違う」** という地獄のバグを引き起こす最大の原因が **「四捨五入の方式」** です。

### Pythonの標準 `round()` は「偶数丸め（銀行丸め）」である！
Pythonで `round(2.5)` と `round(3.5)` を実行してみてください。
```python
>>> round(2.5)
2   # え！？ 3じゃないの？
>>> round(3.5)
4
```
Pythonの組み込み `round()` や NumPyの標準関数は、端数がちょうど `.5` のとき、**最も近い偶数の方へ丸める（Banker's rounding: 銀行丸め）** という仕様になっています。

### C言語の丸めは「0から遠ざかる方向（Round half away from zero）」
一方、C言語の `roundf()` や多くの組み込みDSPハードウェアは、小学校で習う普通の四捨五入、すなわち **「真ん中の `.5` はゼロから遠い方（$+2.5 \rightarrow +3$, $-2.5 \rightarrow -3$）へ丸める」** 実装になっています。

もしPythonの学習スクリプトが「偶数丸め」を使い、マイコンのCコードが「四捨五入」を使っていたらどうなるでしょうか？
**微妙な数値のときに $\pm 1$ LSB だけ値が食い違い、PCで100%正解だったAIモデルが、実機マイコンに乗せた瞬間に誤認識を起こす** のです。

### SEROVの解決策: ビット完全一致関数の導入
この悲劇を防ぐため、Python側の参照実装（`software/acoustic-trainer/features.py`）では、C言語と全く同じ挙動をする専用の丸め関数を自作しています：

```python
def round_half_away_from_zero(values: np.ndarray) -> np.ndarray:
    """実数配列を中間値でゼロから遠ざかる方向へ丸める（C言語と完全一致）。"""
    values = np.asarray(values, dtype=np.float64)
    return np.where(values >= 0.0, np.floor(values + 0.5), np.ceil(values - 0.5))
```

この厳密な配慮のおかげで、SEROVでは **「Pythonホスト環境とESP32-S3実機の間で、量子化後のint8バイト列が 100% 1ビットの狂いもなく完全一致する」** ことが数学的・実験的に証明されています（`test_log_mel.py` 通過済み）。

---

## 4.5 まとめ

- **量子化** とは、小数を粗い整数に丸める処理。精度をほとんど落とさずにメモリを $\frac{1}{4}$ に圧縮できる。
- Arm Cortex-M85の **Helium MVE（ベクトル拡張）** により、`int8` 整数16個を1クロックで超高速並列計算できる。
- SEROVの量子化は `scale = 0.125`, `zero_point = 0` であり、実質的に **「8を掛けて四捨五入するだけ」**。
- PythonとC言語の丸め動作のズレ（偶数丸めの罠）を排除し、**実機とホストのビット完全一致** を保証している。

1フレームあたり「32バイト（int8 × 32bin）」という極限までスリム化された音響特徴量。
次章では、このデータがどのようにしてマイコン間をバトンリレーされ、80フレーム（800ms）のAI入力テンソルに再組立されるのかを追いかけます！
