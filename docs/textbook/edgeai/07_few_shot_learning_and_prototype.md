# 第7章: その場で覚える「現場学習」とプロトタイプ最近傍照合

前章で、CNNモデルが $80 \times 32$ の音響スペクトログラムから、**「64次元のint8埋め込みベクトル（音の指紋）」** を生成する仕組みを学びました。

いよいよ最終章です。
なぜSEROVは「救助笛」「モータ音」といった判定結果を直接モデルから出さず、わざわざ「64個の数値（埋め込みベクトル）」を出力させているのでしょうか？
本章では、ロボットが未知の現場で初めて聞く音をその場で覚える **「現場学習（Few-shot Learning）」** と、超高速な **「プロトタイプ最近傍照合」** の秘密を解き明かします。

---

## 7.1 なぜ「固定の分類モデル」ではダメなのか？

### 実験室のAIが現場で役に立たない理由
PC上でAIを作るとき、多くの人は「クラス分類モデル（最後にSoftmax層をつけて、笛95%、人声3%と確率を出すモデル）」を作ります。
しかし、探査ロボットでこれをやると、現場で必ず手痛い失敗を喫します。

1. **現場ノイズの多様性**:
   - 走行する床の材質（コンクリート、砂利、鉄板、カーペット）、壁の反響、周囲のエアコンや換気ファンの音は、**探査する現場ごとに全く異なります**。
   - 実験室でどんなに高精度に学習させたモデルでも、現場特有の反響やノイズが混ざると、あっけなく誤認識を起こします。
2. **マイコンでは「再学習」ができない**:
   - 「現場で間違えたら、その場で再学習（誤差逆伝播法: Backpropagation）させればいいじゃないか」と思うかもしれません。
   - しかし、ディープラーニングの学習計算（勾配計算や重みの更新）には、推論の数百倍〜数千倍のメモリと計算能力が必要です。マイコンのメモリ（数十KB〜数百KB）では、学習アルゴリズムを動かすことは物理的に不可能です。

### SEROVの答え: 「距離学習（Metric Learning）」
そこでSEROVは、発想を180度転換しました。
**「AIモデルには、クラスを当てさせない。音の特徴を抽出して『似た音同士が近くに集まる64次元の地図』の上にプロットさせることだけに専念させる」** というアプローチです。

---

## 7.2 64次元埋め込み空間の直感的イメージ

### 例え話: 「顔認識」と「指名手配写真」
空港の自動顔認証ゲートを想像してください。
ゲートのAIは、世界中の全人類の顔をあらかじめ学習しているわけではありません。
- AIの役割は、カメラに映った顔から「目と目の距離、鼻の高さ、顎のライン」などをギュッと要約した **「顔の特徴ベクトル（数値の並び）」** を作ることです。
- パスポートのICチップに入っている写真の特徴ベクトルと、今カメラで撮った特徴ベクトルの **「距離（似ている度合い）」** を測り、距離が近ければ「本人である」と判定します。

SEROVの音響AIも、これと全く同じ仕組みです。

```text
               64次元の音響空間 (イメージ図)
  
       救助笛エリア          
         ▲   ★ 救助笛 A
         │   ★ 救助笛 B
         │       ▲ 似た音同士は
         │       │ 近くに集まる！
         │       ▼
         │   ★ 今鳴った音 (テスト音)
         │  
         │                   ● モータノイズ A
         │                   ● モータノイズ B
         │        ■ 足音
         └──────────────────────────────────▶
```

- 救助笛の音は、どんな吹き方をしても「救助笛エリア」の近くにプロットされます。
- 車体のモータノイズは「モータ音エリア」に、障害物の接触音は「衝突音エリア」にプロットされます。

## 7.3 その場で覚える「現場プロトタイプ（Prototype）」

この仕組みの最大の強みは、**「重みの再学習（Backprop）を一切行わずに、現場で新しい音を一瞬で記憶できること」** です。

```text
【現場での学習ステップ（現場プロトタイプ登録）】
 1. 現場に到着後、救助対象の笛を「ピッ！ ピッ！」と2〜3回鳴らしてもらう。
 2. ローバーのCNNモデルが、それぞれの音から64次元ベクトルを計算する。
 3. それらのベクトルの平均値（重心）を計算し、「プロトタイプ p」としてメモリに保存する！
    （計算時間はわずか数ミリ秒、重いモデルの再学習は不要！）
```

`firmware/ra8p1/SoundExplorationRover_CPU0/src/services/acoustic_identifier.h` に定義されているプロトタイプの構造体を見てみましょう：

```c
typedef struct st_acoustic_identifier_prototype {
    B embedding[64];            /**< 64次元のint8プロトタイプ重心ベクトル */
    UW max_squared_distance;    /**< この音として認める許容二乗距離（しきい値） */
    UB class_id;                /**< クラス識別番号（0: 救助笛, 1: 呼気, etc.） */
    BOOL valid;                 /**< プロトタイプ有効フラグ */
} acoustic_identifier_prototype_t;
```

## 7.4 二乗L2距離の超高速計算（`acoustic_identifier.c`）

走行中、未知の音が鳴ると、CNNモデルが最新の64次元ベクトル $e$ を出力します。
ローバーは、登録されているプロトタイプ $p$ との間の **「ユークリッド距離の二乗（二乗L2距離: Squared L2 Distance）」** を計算します。

$$D^2 = \sum_{i=0}^{63} (e_i - p_i)^2$$

実際のC言語実装（`acoustic_identifier.c`）をご覧ください：

```c
EXPORT UW acoustic_identifier_squared_l2(const B * p_embedding, const B * p_prototype) {
    UW squared_distance = 0U;
    for (UW index = 0U; index < 64U; index++) {
        W const difference = (W) p_embedding[index] - (W) p_prototype[index];
        squared_distance += (UW) (difference * difference);
    }
    return squared_distance;
}
```

### なぜこんなに速いのか？
- **割り算も平方根（$\sqrt{\phantom{x}}$）も使わない**: 距離の大小比較をするだけなら、わざわざ重い平方根を計算する必要はなく、二乗のまま比較すれば十分です。
- **純粋な32ビット整数演算**: `float` 演算を一切使わず、引き算・掛け算・足し算だけで完結するため、Cortex-M85なら **わずか数十クロック（1マイクロ秒未満）** で64次元の距離計算が完了します！

## 7.5 しきい値（`max_squared_distance`）による未知ノイズの拒絶

プロトタイプ照合において最も重要なのが、**「未知の音を『知りません』と正しく弾く（拒絶する）こと」** です。

もし単純に「一番近いプロトタイプ」を選ぶだけ（1-NN分類）にすると、足音や風の音など、全く関係ない雑音が鳴ったときでも、無理やりどれかのクラスに分類されてローバーが誤作動してしまいます。

```text
                     ★ 救助笛プロトタイプ
                    ╭─────────────╮
                    │ 許容半径 R  │  ← max_squared_distance
                    │  (合格圏)   │
                    ╰─────────────╯
                           
         ★ 未知の雑音 (一番近いのは救助笛だが、合格圏の外！)
            ──▶ 「一致なし (matched = FALSE)」として安全に無視！
```

`acoustic_identifier.c` では、最も近いプロトタイプを選んだ後、その距離が許容範囲内にあるかを厳格に判定します：

```c
if ((NULL != p_nearest) && (p_output->squared_distance <= p_nearest->max_squared_distance)) {
    p_output->matched = TRUE;  /* 合格圏内！ 目的の音と認定 */
} else {
    p_output->matched = FALSE; /* 遠すぎる！ 未知の雑音として破棄 */
}
```

## 7.6 走行判断（ステートマシン）への統合

こうして得られた判定結果は、第6章で学んだ「停止聴取型ステートマシン（`sound_follow_controller.c`）」へと直結します。

```text
[XVF3800] ──▶ 音源の方向 (DoA) = 右 35°
[AI推論]  ──▶ 音の種類 (Class) = 救助笛 (matched = TRUE, 距離 240 <= 許容値 500)
                    ↓
[走行判断] ──▶ 「右35°から救助笛が鳴った！」と100%の確信を持って確定
                    ↓
[モータ駆動] ──▶ 4輪サーボを右35°へ操舵し、1000ms前進ステップ移動！
```

もし鳴った音がローバー自身の走行音や壁のガタつき音であれば、`matched == FALSE` となり、ローバーはピクリとも動かず静かに聴取（LISTEN）を継続します。
**「音の方向（物理DSP）」と「音の正体（エッジAI）」が完璧に融合** することで、SEROVは迷うことなく目的の音源へと辿り着くことができるのです。

## 7.7 まとめ

- 現場ごとに環境ノイズが異なり、マイコンでは再学習（Backpropagation）ができないため、固定分類モデルではなく **「距離学習（Metric Learning）」** を採用した。
- CNNは音を **64次元の「音の指紋（埋め込みベクトル）」** に射影し、似た音同士を近くに集める。
- 現場で数回音を聞くだけで、その重心を **「プロトタイプ」** として一瞬で記憶できる（Few-shot Learning）。
- **二乗L2距離** の計算はfloatを使わず整数演算だけで行われ、マイクロ秒単位で完了する。
- 許容距離しきい値（`max_squared_distance`）によって未知の環境ノイズを安全に無視し、**真の目的音と確定したときだけ音源方向へ自律走行** する。
