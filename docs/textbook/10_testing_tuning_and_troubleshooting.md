# 第10章: 実機キャリブレーション・テスト・トラブルシューティング

本章では、SEROVの実機を安全かつ確実に動作させるための「物理パラメータの実機校正記録」、e² studioにおける「Live Watchデバッグ必須変数」、および最新の実機検証知見（2026-09-24鳴子追従検証・2026-09-26音響TFLM検証）に基づく「実践トラブルシューティング集」を解説します。

## 10.1 実機キャリブレーション記録と定数の決定

組み込み制御において、カタログスペックの数値を鵜呑みにすると、計算誤差が蓄積して自律走行が破綻します。
SEROVプロジェクトでは、綿密な実機計測によって物理パラメータを固定しています。

### 1. エンコーダ分解能の実機校正（702 counts/rev）
JGA25-370モータのカタログ値は900 counts/revでしたが、実機において以下の厳密な手押し計測を実施しました。

```text
【測定条件】
  ・車体を直線で正確に 2000 mm 手押し（10回反復計測）
  ・車輪外径: 108.00 mm（外周長: 339.292 mm）
  ・左右累積エンコーダカウントの増分を記録
```

| 計測回 | 左車輪 カウント増分 | 右車輪 カウント増分 |
|:---:|---:|---:|
| 1 | 4,208 | 4,166 |
| 2 | 4,145 | 4,000 |
| 3 | 4,098 | 4,113 |
| 4 | 4,116 | 4,122 |
| 5 | 4,090 | 4,113 |
| 6 | 4,145 | 4,170 |
| 7 | 4,176 | 4,181 |
| 8 | 4,122 | 4,139 |
| 9 | 4,188 | 4,179 |
| 10 | 4,138 | 4,134 |
| **平均値** | **4,142.6** | **4,131.7** |

$$\text{counts\_per\_rev} = \frac{\text{カウント増分} \times 339.292\text{ mm}}{2000\text{ mm}}$$
- 左推定値: $702.77\text{ counts/rev}$
- 右推定値: $700.92\text{ counts/rev}$
- 左右平均値: **$701.85\text{ counts/rev}$**（左右差わずか $0.26\%$）

この計測結果に基づき、設定値 `WHEEL_ENCODER_COUNTS_PER_REV` をカタログ値の `900U` から **`702U`** に正式改定しました（`firmware/ra8p1/SoundExplorationRover_CPU1/src/config/drive_config.h`）。

---

### 2. 車体走行幾何と旋回半径計算
実機での旋回円測定から、旋回モデルパラメータを確定しています。

- **車輪半径 $r$**: $54\text{ mm}$（直径 $108\text{ mm}$）
- **実効トレッド幅 $T$**: **$260\text{ mm}$**（車体中心から左右車輪中心まで $130\text{ mm}$）
- **旋回半径 $R$ の計算式（差動二輪モデル）**:
  $$R = \frac{T}{2} \cdot \frac{v_R + v_L}{v_R - v_L}$$
  - $v_R = v_L$: 直進（$R = \infty$）
  - $v_R = -v_L$: 超信地旋回（スピンターン、$R = 0$）
  - 片輪停止（$v_L = 0$）: 車体中心の旋回半径 $R = 130\text{ mm}$

---

### 3. サーボ中央値（ニュートラル）の調整
DS3225MGサーボは個体ごとにホーンのスプライン噛み合わせ誤差（$\pm$数度）があります。
1. 車輪を床から浮かせ、CPU1へ $0^\circ$ 指令を入力。
2. ホーンを直進に最も近い歯位置に取り付け。
3. Live Watchで `g_servo_center_trim_us[0..3]` を $\pm 5 \sim 10\text{ }\mu\text{s}$ 単位で微調整し、直進位置へ合わせる。
4. 決定値を `src/config/servo_config.h` の `SERVO_CENTER_TRIM_US_FR/FL/RR/RL` へ書き込む。

## 10.2 Live Watch デバッグ必携シンボル集

実機動作中にe² studioの **Live Watch（変数リアルタイム監視機能）** に登録すべき最重要変数は以下の通りです。

### CPU0 側コンテキスト（思考・センサ・推論・ナビゲーション）

| 変数名 | 期待される正常値 | 監視の目的・トラブル検知 |
|---|---|---|
| `g_task_think_state` | `LISTEN`, `MOVE_STEP`, `SPIN_STEP` 等 | 思考ステートマシンの現在状態。`FAULT` の場合は異常停止 |
| `g_task_think_fault_flags` | `0x00000000` | CPU0でラッチされた全障害ビットマップ |
| `g_task_think_sensor_fresh` | `1` (TRUE) | センサデータ鮮度。200ms以上途絶すると `0` になり即時停止 |
| `g_task_think_sensor_rule` | `SENSOR_FORWARD`, `PIVOT_*` 等 | 障害物回避コントローラが選択した現在の走行ルール |
| `g_task_infer_available` | `1` (TRUE) | 音響推論タスクの正常稼働状態 |
| `g_task_infer_tflm_available`| `0` (ベースライン) / `1` (TFLM) | TFLM音響モデルの初期化状態 |
| `g_task_infer_match_count` | 目的音検知ごとに増加 | 現場学習見本との一致回数 |
| `g_task_think_source_range_mm`| 数百〜数千 mm | 推定音源までの直線距離（bearing-only推定） |
| `g_task_think_source_bearing_deg`| $-180^\circ \sim +180^\circ$ | 車体から見た音源の相対方位角（右正） |
| `g_task_think_arrival_state` | `APPROACHING` / `ARRIVED` | 音源への接近・到着判定段階 |
| `g_task_acoustic_link_usb_configured` | `1` | XIAO ESP32-S3とのUSB CDC接続完了フラグ |

### CPU1 側コンテキスト（駆動・アクチュエータ・安全）

| 変数名 | 期待される正常値 | 監視の目的・トラブル検知 |
|---|---|---|
| `g_task_actuator_update_count` | 連続増加（1msごと） | 1ms制御ループの生存確認 |
| `g_task_actuator_period_last_ms` | `1` (ms) | 制御ループの実周期。1以外の値が頻発すると負荷過大 |
| `g_actuator_service_applied_sequence` | 連続増加（50msごと） | CPU0から正常に確定指令が届いているかを確認 |
| `g_actuator_service_fault_flags` | `0x0000` | CPU1障害フラグ。**Bit 0（0x0001）は1500msタイムアウト** |
| `g_drive_left_duty_permille` | 走行時非ゼロ | 左モータへの実適用PWM Duty（‰） |
| `g_drive_right_duty_permille` | 走行時非ゼロ | 右モータへの実適用PWM Duty（‰） |
| `g_encoder_left_rpm_x10` | 走行時非ゼロ | 左エンコーダ実測回転数（$0.1\text{ RPM}$ 単位） |
| `g_encoder_right_rpm_x10` | 走行時非ゼロ | 右エンコーダ実測回転数（$0.1\text{ RPM}$ 単位） |

## 10.3 実践トラブルシューティング集（実機知見）

### 障害1: モータやサーボが全く動かない
- **原因①（DIPスイッチ）**: EK-RA8P1の `SW4-4` がOFFのままになっている。
  - **対策**: 電源を切り、`SW4-4` を **ON** にする（Arduinoコネクタ端子を有効化）。
- **原因②（電源供給）**: モータ駆動用12V電源やサーボ用電源がOFF、またはGNDが共通化されていない。
  - **対策**: 電源をONにし、スターGND結線を確認。
- **原因③（指令タイムアウト）**: CPU1のLive Watchで `g_actuator_service_fault_flags` の Bit 0 が立っている。
  - **対策**: CPU0の `task_command` が正常に動いているかを確認。

### 障害2: I2Cセンサが認識されない（`valid_flags != 0x0F`）
- **原因①（DIPスイッチ）**: EK-RA8P1の `SW4-5` がONになっている（I3C側が選択されている）。
  - **対策**: 電源を切り、`SW4-5` を **OFF** にする（IIC1を有効化）。
- **原因②（SCL端子の破損）**: Arduino標準端子 `J24-10 (P512)` が破損している。
  - **対策**: 配線を予備端子 **`J23-8 (P312 / D7)`** へ移設し、CPU0のFSP/GPIOドライバ設定を確認。

### 障害3: 後方の音に対して逆方向に旋回してしまう（DoA極性の反転）
- **原因**: XVF3800のマイク配置・向きの変更に伴い、前方DoAと後方DoAで符号規則の不整合が発生していた。
- **対策**: `sound_follow_controller.c` において、前方はDoAの符号反転、後方は同符号として車体相対角（右正: $+1^\circ \sim +180^\circ$、左負: $-1^\circ \sim -180^\circ$）へ厳密に統一。Rover Monitorの音響線描画と完全に整合。

### 障害4: 壁際旋回中に片輪がスタックして停止・脱出できない
- **原因**: 左右の平均並進速度でスタック判定していたため、片輪が乗り上げて停止（0 RPM）し、反対輪だけが回転している状況を見逃していた。
- **対策**: 最新の `task_think` に導入された **片輪スタック脱出ロジック**（片輪20 RPM以下・反対輪30 RPM以上が700ms継続で `SENSOR_BACKUP` 発動）により自動解消。

### 障害5: 真後ろ（$\approx 180^\circ$）境界で旋回方向が激しく振動する
- **原因**: 真後ろ $\pm 180^\circ$ 付近のわずかなDoAノイズで左旋回と右旋回が反転を繰り返していた。
- **対策**: 車体相対角の絶対値が $160^\circ$ 以上のときは、**左右ToFのクリアランスが広い側（差が150mm以上）へ旋回方向を固定** し、旋回開始後はDoAの微小変動だけで方向を反転しないラッチ制御を適用。

### 障害6: TFLM音響モデルが起動時に初期化失敗する
- **原因**: Kerasからの変換時に未登録の数学演算子（7個）が混入した、またはアリーナサイズが不足（112 KiB未満）。
- **対策**: 実機本番ファームウェアでは堅牢な **192次元DSP要約照合ベースライン（`CPU0_USE_ACOUSTIC_EMBEDDING_TFLM = 0`）** を採用していることを確認。TFLMを再評価する場合は、`acoustic_tflm_runtime.h` のアリーナサイズを 128 KiB に設定し、`review_acoustic_tflm_host.py` で事前検証する。

## 10.4 まとめ

- 実測に基づく校正（702 counts/rev, 260mm トレッド）により、理論値とのズレを排除した高精度制御を実現。
- Live Watchにより、デュアルコア間の通信状態、センサ健全性、音源位置推定、およびAI推論状態をリアルタイム診断可能。
- 幾多の実機走行検証（2026-09-24, 2026-09-26）から得られた知見（DoA極性、片輪スタック、端子破損、AIベースライン化）が、システムの驚異的な堅牢性を支えています。
